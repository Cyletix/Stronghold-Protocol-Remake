# 资料、规则与代码复现主线

本项目的首要工作不是凭观感补齐一个相似玩法，而是从现有 APK、gamedata、资源、客户端代码、网络行为、官方文案和可重复实验中提取可追溯证据，再把规则与资源复现为可验证代码。任务状态仍以 `assets/task/T-*.md` 为准；本文只定义长期方法和取舍原则。

## 主线顺序

1. **定位原始资料**：先确认赛季、版本和资源归属，区分初版 `act1autochess`、「盟约」`act1vautochess` 与后续版本，避免混用同名关卡、干员池、策略头像和规则。
2. **形成可重复提取**：把人工发现落实为 `tools/**` 中可重复运行的提取或检查程序，记录输入路径、关键字段、版本、输出与缺口。
3. **还原规则模型**：为地图、阶段、经济、盟约、策略、技能、天赋、装备、敌人和联防分别建立“来源字段 → 规则语义 → 边界 → 证据等级”的映射。
4. **接入代码复现**：生成数据进入 `web/**` 后，由明确 consumer 实现；不得用难以追溯的手写常量静默覆盖已经存在的源数据。`server/**` 与客户端补丁只保留历史研究，不进入产品主链。
5. **对照验证**：用数据检查、smoke、确定性场景、客户端实验和视觉对照分别验证数据、行为与表现；发现差异时回到证据或模型层定位，不以调测试或文档掩盖实现错误。

## 如何判断规则合理

一条规则可以作为实现依据，至少应回答以下问题：

- **版本是否一致**：证据属于当前复现的「卫戍协议：盟约」，还是同名但规则不通用的初版/二期内容？
- **来源能否定位**：能否指出具体文件、键、资源名、函数、网络字段、教学文案或可重复实验？
- **语义是否闭合**：触发条件、状态变化、数值单位、默认值、上限、回合边界、失败路径和多人/BOSS 差异是否明确？
- **多份证据是否相容**：数据、资源、客户端行为和文案是否互相支持；如有冲突，是否记录了冲突而非自行择一？
- **代码能否追溯**：生成字段与运行时 consumer 之间是否有清楚映射，生成物能否从源重新构建？
- **能否被证伪**：是否存在一个具体检查或实验，可以区分“实现正确”和“只是看起来合理”？

判定规则：

- 直接数据、资源、客户端代码、网络行为或可重复实验支持的结论按 `Verified` 管理。
- 多个迹象支持但仍缺直接确认的结论按 `Inferred` 管理，并在规格和实现处保留不确定性。
- 仅用于指导研究的解释按 `Hypothesis` 管理，不直接作为实现正确性的标准。
- 截图适合验证可见结构、位置、颜色和动画观感；不能单独证明精确数值、隐藏状态机或服务器规则。
- “运行正常”“视觉相似”只能证明对应层次，不自动证明资源、数据和规则已经正确。

## 单条规则的完成标准

一条规则只有在以下链路闭合后才算完成：

1. 来源与版本已记录；
2. 证据等级已确定；
3. 规则的触发、状态、边界和例外已描述；
4. 提取脚本或复现实验可以重复；
5. 生成数据与代码 consumer 可以对应；
6. 至少一个正例和一个关键边界/反例通过验证；
7. 已知缺口和客户端差异没有被静默隐藏。

## 资料账本

数据与资源现状统一在 `docs/data-inventory.md` 与 `docs/data-progress.md` 维护。每类资产至少记录：

| 项目 | 必填内容 |
|---|---|
| 复现对象 | 地图、规则、资源或协议的明确名称与赛季 |
| 原始来源 | 文件/Bundle/代码/网络/文案/实验的具体定位 |
| 提取程序 | `tools/**` 中可重复运行的入口；尚无则写明 |
| 生成物 | `web/**`、`server/**` 或研究文档中的目标资产 |
| Consumer | 实际读取生成物的模块或函数 |
| 证据等级 | Verified / Inferred / Hypothesis |
| 当前状态 | 未定位 / 已定位 / 已提取 / 已接入 / 已验证 |
| 验证证据 | checker、smoke、实验、截图对照或客户端记录 |
| 已知缺口 | 尚未获取或无法确认的字段、行为与版本差异 |

## 抓大放小

按以下优先级推进；同级内部再按依赖顺序处理：

1. **P0 研究与数据主干**：版本归属、资料账本、提取链、规则证据和生成物可追溯性。
2. **P0 可玩闭环**：正确关卡与阶段、地图分区、镜头、出怪、移动/攻击、胜负和回合转换。
3. **P1 系统规则**：商店经济、盟约、策略、技能、天赋、装备、召唤物、复活与特殊敌人。
4. **P2 小型缺陷与表现**：单个弹窗、卡片、动画、音量、素材缺失和视觉细节。
5. **P3 工程治理**：不改变行为的模块拆分、清理和重构；只在相关机制与验证稳定后进行。

小 bug 若阻断 P0/P1 的验证或可玩闭环，提升到其所阻断任务中处理；否则不得抢占主线。
