# 规则编写方法
%%MetaCraft%%

写规则前先问三件事：这条是 Agent 不知道的吗？它值得占用这些上下文吗？它需要固定限制，还是只需要判断原则？

## 简洁至上

- 上下文窗口是公共资源。默认 agent 已经很聪明，只补充它缺的领域知识。
- 删：重复表述、泛泛的"要全面/要简洁/一步步想"、不改变行为的例子、agent 已可靠执行的流程、无关工具。
- 留：用户可见结果、成功标准、停止条件、安全/权限/证据约束、工具路由、输出形状。

## 自由度匹配

- 高自由度（文本原则）：多方法都有效、靠上下文判断。
- 中自由度（带参伪代码/脚本）：有首选模式、允许少量变化。
- 低自由度（固定脚本、少参数）：操作脆弱易错、必须一致、必须按序。
- 隐喻：窄桥+悬崖要护栏（低自由度），开阔地多条路（高自由度）。同步脚本是低自由度，写作判断是高自由度。

## 绝对规则与决策规则

- 绝对规则（必须/禁止/不得）：只用于真正不变量——安全、权限、必填字段、绝不该发生的动作。
- 决策规则（当 X 时 → 做 Y）：用于判断调用——何时搜索、询问、用工具、停止迭代。
- 能用决策规则就别用绝对规则；互相冲突的绝对规则比缺失细节更糟。

## 结果优先 + 停止条件

- 描述目标而非规定每一步，给出"好"的样子。
- 工作流写清成功标准与停止条件；局部规则只补充会改变决策的边界，不重复全套流程。

## 验证完整性

- 修改授权、停止条件或工作流路由时，用代表任务检查正常执行与边界情况；行为检查只给任务和实际适用规则，不提供预期答案。
- 涉及多个耦合规则且有独立复核价值时，可使用子代理；简单措辞、链接或格式修正做局部检查即可。没有可用子代理不是停止已授权工作的理由。
- 验证通过后停止扩充规则；只有新的失败证据才需要继续修改。

## 增量迁移

- 不一次重写整套规则。先缩小目标、运行代表样例、删除临时说明，只增加必要的修正规则，再运行样例。
- 调试规则行为时尽量一次只改变一个主要变量，否则分不清行为变化来自模型、推理设置、指令还是工具；必须同时修改强耦合契约时，将其作为一个明确变更集并统一验证。
