# Review
## 约束
独立审查请求默认只读，不修改文件、提交、推送或向外部发布评论。实施任务中的自检沿用原有修复授权，发现本次改动导致的问题后继续修复和验证。
## 审查步骤
1. 依据当前请求确定范围和验收条件，按 `AGENTS.md` 读取相关局部规则；使用标准任务时再读取对应 task 文件.
2. 看完整 diff 和足够上下文, 理解每个变更路径.
3. 找本次变更引入的具体回归、契约违反和未闭合影响; 找到第一个问题后继续看完整个 diff.
4. 核对相关测试、调用点、schema、配置和其他实际依赖, 确认每个发现真实且可执行.
## 报告条件
- 对正确性, 安全, 性能, 可维护性或明确的 requirement/contract 有实质影响.
- 离散, 可执行.
- 由本次变更引入 (非既有问题).
- 能从变更内容, 实际依赖或可验证证据说明受影响场景.
- 作者知道后大概率会修.
不报: 投机性担忧, 既有问题, 当前 task 明确要求且未违反其他 contract 的行为变化, 不挡路的风格小瑕疵.
## 输出格式
按严重度排序, 每个问题一条:
`[P1] 命令式标题 — 路径:行`
标题后一段话说明受影响场景与为何错. 引用范围尽量小, 且与 diff 重叠.
优先级: P0 发布阻断/致命; P1 应立即修; P2 应修; P3 低影响仍值得修.
无发现时直接说明；存在影响结论的验证缺口时简要列出，不补充假设性风险。

## 卫戍协议审查项

- 涉及玩法、架构或研究结论时，核对相关 `docs/mode-spec.md`、`docs/architecture.md`、`docs/findings.md`；检查是否把 Inferred/Hypothesis 写成确定事实，或用“已经实现”替代客户端一致性证据。
- 涉及候选区的 UI 变更检查 `tile_achand` 架构及候选角色与战场实体解耦；视觉验收使用任务指定的 `draft/` 对照，并检查调试残留。
- 任务工作流变更必须确认只有 `assets/task/T-*.md` 是当前状态源，旧归档不能重新参与调度。
