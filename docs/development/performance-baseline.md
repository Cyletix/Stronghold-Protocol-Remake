# 浏览器性能基线

## 用途

`web/bench/perf.html` 是纯 Web 架构整改的固定种子压力场景。它用于回答两件事：当前 Canvas2D 路径的成本主要落在哪里，以及后续重构是否真的降低成本。

基准不会导入或修改一局游戏状态，也不把合成数据当作玩法证据。下列负载复现的是整改前热路径；当前游戏已有缓存与池化，不能把旧负载说明当成当前实现清单：

- 每名干员通过 `filter`、`sort` 扫描所在战场全部敌人；
- 大范围攻击扫描全部敌人，四战场合计每模拟秒 200 次；
- 敌人、弹道和粒子采用对象数组并在 tick 末用 `filter` 重建；
- 地形、单位和特效先逐帧重画到整张离屏场景，再以 24×24 共 576 个 `drawImage` 分块透视贴回每块战场。

## 固定负载

基准依次运行单战场和四战场场景。四战场总量为 64 名干员、320 个敌人、1500 个弹道和 4000 个粒子；单战场使用相同总对象量，用来区分“对象规模”与“战场/合成次数”的影响。

每个场景预热 30 帧，再采样 180 帧，分别记录模拟、渲染与两者合计的 p50、p95、最大值和均值，并通过 Long Tasks API 记录浏览器长任务。每个样本在独立的 `requestAnimationFrame` 中执行，避免基准驱动器自行把多帧合并成一个长任务。随机数种子固定为 `0x51a7f00d`。

## 运行

启动本地静态服务后，在正常桌面 Chromium 浏览器打开：

```text
http://127.0.0.1:8000/bench/perf.html
```

页面完成时，`body[data-benchmark-state="complete"]` 和 `window.__PERF_RESULT__` 可供人工检查或自动采集。基准固定创建 1920×1080、DPR 1 对应的绘制表面；报告同时记录窗口视口、实际绘制表面和 DPR。不同机器或不同 DPR 的结果不能直接横向比较。

## 解释边界

该场景是确定性的工程回归负载，不是完整玩法录像，也不直接预测最终四人模式帧率。它刻意隔离素材解码、DOM 更新、音频和垃圾回收偶发峰值，因此实际游戏只会多出这些成本。是否引入 WebGL2 或 Worker，应依据分层、裁剪、空间索引和池化完成后的同一基准复测，而不是依据主观观感。

## 2026-09-05 整改前基线

环境：Windows 10、Chromium 152、DPR 1，实际绘制表面 1920×1080。自动化承载窗口视口为 958×708，但基准没有按该窗口缩小 backing store；所有 Canvas2D 操作仍在报告中的 1920×1080 绘制表面执行。结果不能替代用户机器全屏浏览器的最终验收。

| 场景 | 模拟 p95 | 整图重绘 p95 | 24×24 分块合成 p95 | 渲染 p95 | 合计 p95 | >50ms 帧 / 长任务 |
|---|---:|---:|---:|---:|---:|---:|
| 单战场，同一总对象量 | 1.3ms | 1.5ms | 2.0ms | 3.2ms | 4.3ms | 0 / 0 |
| 四战场，同一总对象量 | 0.7ms | 2.0ms | 5.8ms | 7.6ms | 8.0ms | 0 / 0 |

本机合成压力场景在预算内，但这不是“现有游戏已经能稳定承载四人同屏”的结论。四战场模拟反而更快，是因为对象被分到四个较小的全量扫描集合；渲染则由单战场 3.2ms 增至 7.6ms，其中仅透视分块合成就占 5.8ms。当前最需要先改的是渲染结构：每块战场每帧 576 次 `drawImage`，四块战场达到 2304 次，并且静态地形随动态对象一起重画。真实头像、地形纹理、DOM HUD、音频和 GC 峰值加入后，剩余余量会继续缩小。

### 本轮对象预算

以下数值是下一阶段必须持续通过的总量预算，也是初版质量档位的上限：

- 64 名干员、320 个活跃敌人；逻辑实体不得因超预算静默丢失，屏外实体只允许降低渲染频率。
- 1500 个可见弹道；伤害结算必须与视觉弹道分离，视觉池满时允许合并或省略低优先级轨迹。
- 4000 个可见粒子，四战场各 1000 个软配额；池满时覆盖最低优先级装饰粒子。
- 每模拟秒 200 次范围查询/伤害事件；下一阶段必须用空间索引替代全数组扫描。

这组结果确立了整改顺序：先拆静态地图与动态层、取消逐战场整图逐帧重画并减少透视分块提交；随后再用空间索引与对象池消除规模增长和 GC 风险。当前数据没有证明需要立刻切换 WebGL2 或 Worker。

## 2026-09-05 分层渲染复测

同一 Chromium、1920×1080 绘制表面再次运行固定负载，并在同一次运行中比较旧式合成与静态地形缓存预览：

| 四战场管线 | 模拟 p95 | scene 重绘 p95 | 分块合成 p95 | 渲染 p95 | 合计 p95 | 渲染均值 |
|---|---:|---:|---:|---:|---:|---:|
| 旧式整图 | 0.7ms | 1.9ms | 6.4ms | 8.2ms | 8.8ms | 7.644ms |
| 静态地形缓存 + 动态层 | 0.7ms | 1.7ms | 7.0ms | 8.4ms | 8.8ms | 7.227ms |

缓存使渲染均值下降约 5.5%，但 p95 没有下降。这个负结果同样重要：仅缓存静态地形不能解决高档质量下每帧 2304 次动态层透视分块，分块合成仍是主瓶颈。当前实现因此同时提供 16×16 与 12×12 的平衡/低档质量，以及可见对象裁剪；后续四 viewport 实装时必须继续减少高档动态层的分块提交，不能把“已经分层”等同于“性能问题已经解决”。

## 2026-09-13 进图 GPU 负担与黑屏反馈

用户在 `20260913-202129-2c18e6` 包反馈选择策略进图时 GPU 高负荷、间歇黑屏。1920×940 实际页面未复现驱动重置或持续黑屏，因此不能把显卡、内存不足认定为根因；但源码与页面证实旧渲染器仍为全部地图区段分配两张离屏画布，并每帧透视提交整图动态层。CPU 核心数/系统 RAM 不能作为 GPU 高档性能的依据。

现仅为 `battleClipRect()` 所在战区分配表面，以原地图坐标平移绘制，保持部署命中与相机逆变换；共享 Boss/联防仍覆盖相通的两侧。单表面限制为 2,097,152 像素与单边 4096 像素，低于逻辑尺寸时也允许缩采样。纹理大小按镜头目标确定，避免插值时反复换尺寸。默认自动档改为 balanced，high 仍可显式选择；隐藏页不提交渲染，空准备场不合成透明动态层。Canvas 上下文丢失会使地形缓存失效并降到低档，恢复后重画；离屏绘制异常通过 finally 恢复主画布引用，屏幕保留上次成功帧并记录错误。

同一视口、盟约Ⅱ第1图的实际浏览器观测：

| 项目 | 修改前 | 修改后 |
|---|---:|---:|
| 普通准备场单张离屏表面 | 2058×1862 | 1274×686 |
| 敌人预览单张离屏表面 | 3087×2793 | 882×490 |
| 稳定预览的动态透视提交/帧 | 576 | 144 |
| 无单位、悬停或拖动的空准备场动态提交 | 576 | 0 |

预览两张 RGBA 离屏表面的理论像素存储从约65.8 MiB降为3.3 MiB，不等于浏览器进程总内存或驱动实际显存。新 `canvas#cv` 的 `data-render-ms`、`data-warp-draws`、`data-scene-size`、`data-render-error`、`data-context-losses` 可定位提交耗时和异常；render-ms 是 CPU 提交耗时，不能当作 GPU 耗时或保证60FPS。实际浏览器验证覆盖策略进图、预览、候选采购、高台部署/朝向与首轮结束；上下文丢失恢复是注入事件回归，未人为触发驱动崩溃。

`tools/_render_surface_smoke.js` 检查264组实际地图/视角/分辨率组合、缓存命中、纹理预算、插值尺寸稳定、空场无效提交、异常后的画布归属与恢复；另保留镜头逆变换、共享战场、技能/计时专项回归。本轮没有证明用户机器上的所有间歇黑屏均已消失，仍需该机器复测。
